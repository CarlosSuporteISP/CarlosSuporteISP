# ✅ Repository quality checklist

Use this checklist for every project you want recruiters or the open-source community to evaluate.

## Positioning

- [ ] The repository name is clear and professional.
- [ ] The first paragraph explains the problem and the value of the project.
- [ ] The README identifies whether the project is production-ready, a lab, a fork or a proof of concept.
- [ ] Original work is clearly distinguished from upstream work.

## Documentation

- [ ] English README is available.
- [ ] Portuguese README is available when useful.
- [ ] Architecture or topology diagram exists.
- [ ] Compatibility matrix exists.
- [ ] Installation is reproducible.
- [ ] Configuration examples are sanitized.
- [ ] Troubleshooting section exists.
- [ ] Security and rollback notes exist.
- [ ] Screenshots or sample output are current.

## Engineering quality

- [ ] License is defined.
- [ ] Changelog exists.
- [ ] Tagged releases exist.
- [ ] CI validates scripts, formatting or containers.
- [ ] Secrets are never committed.
- [ ] Shell scripts use safe modes where appropriate.
- [ ] Docker images have pinned versions and health checks.
- [ ] Dependencies are documented.

## Community

- [ ] CONTRIBUTING.md exists.
- [ ] Bug and feature issue forms exist.
- [ ] Discussions are enabled when appropriate.
- [ ] Roadmap or milestones are visible.
- [ ] `good first issue` tasks exist.
- [ ] Upstream attribution is complete for forks.
- [ ] Pull requests and issues receive clear technical responses.

## Recruiter signal

- [ ] The repository is pinned when it represents current strengths.
- [ ] The description contains searchable keywords.
- [ ] GitHub topics are configured.
- [ ] A social preview image is configured.
- [ ] The README explains what you personally designed or implemented.
- [ ] Outcomes, scale and lessons learned are stated without exposing customer secrets.
